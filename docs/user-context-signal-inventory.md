# Какие данные можно использовать для защиты от мошенничества

**Проверено:** 21 ноября 2026 г.  
**Текущий приоритет ContextShield:** Android; разделы Windows сохранены как справочный материал для будущего этапа.  
**Цель:** инвентаризация доступных источников контекста, их реальной антифрод-ценности, системных разрешений, ограничений и рекомендаций по приватности.

## Короткий вывод

Самый ценный сигнал — не «как можно больше данных с телефона», а **событие перевода из самого банка**: кому, сколько, впервые ли переводит пользователь, менялись ли реквизиты и на каком шаге началась операция. Только интеграция с банком может надёжно связать контекст сообщений с конкретным переводом и действительно задержать или остановить его.

Для самостоятельного приложения без банка наиболее разумная последовательность такая:

1. **Уведомления выбранных пользователем Android-приложений** — текущий автоматический источник, но ОС/мессенджер могут скрыть текст и не дают гарантированную личность отправителя.
2. **Короткая проверка UsageStats по событию** — отдельный opt-in-кандидат: только после уже возникшего риск-эпизода проверить, открывалось ли известное приложение удалённой помощи в ближайшие минуты. Не собирать историю приложений.
3. **System contact picker для out-of-band проверки** — пользователь выбирает один сохранённый контакт и может позвонить по известному номеру; приложение не импортирует адресную книгу и не переносит доверие по нику.
4. **Событие перевода из демо-банка** нужно для демонстрации; реальный transaction gate возможен только через официальный SDK/backend партнёра.
5. Sharesheet/ручная вставка, Accessibility, MediaProjection и фоновые clipboard-события не являются текущим путём MVP. Windows-разделы — справка для возможного будущего расширения, не текущий фокус.

Ни Android, ни Windows не дают стороннему приложению универсальный скрытый API для чтения личных чатов, внутренней базы мессенджера, всех банковских экранов или аудио звонков. Сбор должен быть видимым и управляемым пользователем. Больший объём наблюдения сам по себе не повышает точность: он также приносит больше шума, ложных тревог, расхода батареи и риска утечки.

## Как читать список

- **P0 — основной MVP:** высокая ценность и реалистичная/понятная интеграция.
- **P1 — полезное расширение:** добавлять после проверки P0 и отдельной оценки разрешений.
- **P2 — только узкий opt-in-сценарий:** возможно технически, но широкое постоянное включение не рекомендую.
- **Не собирать:** непропорционально, не нужно для цели, ненадёжно или создаёт неприемлемый риск.

«Данные доступны API» не означает «их всегда видно»: источник может не выдать текст, пользователь может отозвать доступ, приложение-источник может скрыть содержимое, а производитель телефона или настройки приватности могут изменить поведение.

## 1. Android

### 1.1 Системные уведомления — P0, уже есть в прототипе

`NotificationListenerService` получает события публикации и удаления уведомлений, а `StatusBarNotification` содержит, среди прочего, пакет приложения-источника и время публикации. Если мессенджер сформировал уведомление в стиле `MessagingStyle`, уведомление иногда содержит несколько новых сообщений, отправителя и заголовок беседы.

**Что полезно для модели:**

- название/идентификатор приложения-источника;
- заголовок, текст, расширенный текст и доступные сообщения из `MessagingStyle`;
- доступное имя собеседника/заголовок беседы и признаки группового сообщения — только как краткоживущий display context, не как identity key;
- время публикации уведомления и порядок появления событий;
- видимые ссылки, номера, денежные суммы и просьбы о действии в тексте.

**Что это даёт:** локально связать серию сигналов — сначала срочное сообщение, потом звонок, затем просьба добавить нового получателя или установить приложение удалённого доступа. Временная последовательность часто полезнее одного отдельно взятого сообщения.

**Ограничения и нюансы:**

- Доступ включается пользователем в системных настройках и по своей природе широк. Фильтр «учитывать только выбранные мессенджеры» внутри приложения уменьшает последующую обработку, но не превращает системное разрешение в точечное разрешение для одного чата. Это нужно честно объяснить на экране настройки.
- ОС даёт только то, что приложение решило показать в уведомлении. Предпросмотр может быть выключен; уведомление может содержать только «Новое сообщение»; часть мессенджеров не публикует полный текст; уведомление может быть сгруппировано или удалено.
- `postTime` — время публикации уведомления ОС, а не обязательно время написания сообщения. Не следует трактовать задержку доставки как время отправки.
- `MessagingStyle` позволяет приложению-источнику добавить несколько сообщений и исторический контекст, но не гарантирует полный чат. Имя, переданное уведомляющим приложением, не является криптографически подтверждённой личностью.
- Изменяемый ник не позволяет решить, тот ли это человек: совпавшее имя не переносит trusted status, а новое имя само по себе не является сигналом мошенничества. Listener обычно не получает официальный stable account ID мессенджера.
- На Android 15 система скрывает распознанные одноразовые коды из уведомлений, доступных недоверенным notification listeners; во время демонстрации экрана уведомления также могут быть скрыты. Нельзя пытаться обходить эту защиту — код подтверждения не нужен классификатору мошенничества.
- Режим энергосбережения, перезапуск службы и особенности OEM могут привести к задержке/пропуску события. Нужно показывать статус «источник подключён», а не обещать 100% доставки.

**Рекомендация:** оставить этот источник включённым по явному согласию, дать список исключений приложений и кнопку паузы/очистки. Разбирать данные сразу на устройстве; хранить короткий след признаков, а не архив чатов. [Android NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [StatusBarNotification](https://developer.android.com/reference/android/service/notification/StatusBarNotification), [MessagingStyle](https://developer.android.com/reference/android/app/Notification.MessagingStyle), [изменения приватности Android 15](https://developer.android.com/about/versions/15/behavior-changes-all).

### 1.2 Системное «Поделиться» — технически доступно, но не входит в текущий MVP

Приложение может объявить себя получателем текста, URL или файла через Android Sharesheet. Пользователь в Telegram, WhatsApp, SMS, почте или браузере сам выбирает «Поделиться → ContextShield».

**Что можно проверить:** конкретный выбранный фрагмент текста; ссылку; выбранное изображение/скриншот; при необходимости пользователь может добавить ответ на короткие вопросы («это новый получатель?», «просили держать просьбу в тайне?»).

**Ценность:** источник работает и там, где ОС не показывает текст в уведомлении, но действие происходит только для конкретного элемента, выбранного человеком. Это хорошее покрытие множества приложений без фонового чтения их баз данных.

**Ограничения:** пользователь должен сделать явное действие; приложение получает только переданные данные и не видит предыдущую переписку автоматически. Не все приложения предлагают Share для каждого элемента. Нужно ограничить MIME-типы, размер и время жизни переданного файла, не сохранять оригинал без необходимости.

**Рекомендация для текущего scope:** не делать Sharesheet/ручную вставку основным или обязательным способом анализа. Если позднее команда решит добавить разовую проверку изображения/URL, реализовать отдельным opt-in-потоком. [Android: приём данных от других приложений](https://developer.android.com/develop/ui/compose/sharing/receive).

### 1.3 Экран/интерфейс других приложений через AccessibilityService — P2, не включать по умолчанию

Служба специальных возможностей может получать структуру интерфейса и текст доступных элементов, когда пользователь явно включил её в настройках. В отдельных приложениях она способна видеть больше текста, чем уведомление.

**Потенциальная ценность:** прочитать экран беседы или платёжного сценария, если приложение не опубликовало нужное в уведомлении.

**Ограничения и риски:**

- это очень широкое разрешение: потенциально видны сообщения, названия счетов, суммы, одноразовые коды и другие элементы разных приложений;
- не каждый интерфейс доступен: приложение может не отдавать узлы, рисовать текст в Canvas/WebView, скрывать экран, помечать данные чувствительными или менять структуру после обновления;
- Android и Google Play рассматривают Accessibility API как чувствительный интерфейс. Приложение, не являющееся специализированным средством доступности, должно декларировать применение, явно объяснять его до включения и получать утвердительное согласие. Нельзя выставлять флаг `isAccessibilityTool`, если продукт не является инструментом доступности для людей с инвалидностью;
- ручное включение не заменяет объяснение целей, области экранов, локальной обработки, хранения и отключения. Автоматическое нажатие «Перевести» / управление чужим банком этим сервисом добавлять не следует.

**Рекомендация:** не включать в публичную сборку MVP. Если позднее нужен узкий опыт «проверьте открытый экран», сначала оценить банковскую интеграцию, правила Play, демонстрацию согласия, allowlist приложений и локальную фильтрацию. [Android AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService), [правила Google Play для Accessibility API](https://support.google.com/googleplay/android-developer/answer/16558241), [Google Play User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311).

### 1.4 Использование приложений через UsageStats — Android MVP candidate, только отдельный opt-in

`UsageStatsManager` может вернуть агрегаты использования приложений и события использования за ограниченный недавний период. Для этого пользователь вручную выдаёт специальный доступ «Доступ к истории использования» в настройках; это не обычный runtime-диалог.

**Потенциальные признаки:** какие приложения были активны рядом с запросом перевода; использовалось ли приложение удалённого доступа перед банковским сценарием; переключался ли пользователь между мессенджером и банком.

**Чего API не даёт:** текст чата, нажатия клавиш, пароль, точный экран, адресата или причину открытия приложения. События UsageStats хранятся системой лишь несколько дней, а доступ зависит от состояния разблокировки устройства.

**Ценность/риск:** может добавить слабый временной признак «после звонка открыли AnyDesk и банк», но не доказывает мошенничество: удалённое приложение может быть установлено для поддержки родственника, а порядок приложений — обычен. Это тоже подробная история поведения.

**Рекомендация:** провести узкий feasibility spike как дополнительную Android-функцию: после высокорискового notification episode или начала mock-bank transfer сделать один запрос за короткое окно (например, 15 минут), сопоставить только allowlist remote-support package IDs и сохранить только boolean `remote_access_app_opened` + грубое время. Никакого polling/архива usage/QUERY_ALL_PACKAGES. Включать в итоговый score только после проверки на целевых OEM и измеренного выигрыша при ложноположительном контроле; если ограничить доступ или надёжность нельзя — оставить выключенным. [UsageStatsManager API](https://developer.android.com/reference/android/app/usage/UsageStatsManager).

### 1.5 Скриншот/запись экрана через MediaProjection + OCR — P2, только разовый выбор пользователя

MediaProjection может захватить выбранное приложение или экран после системного подтверждения. На Android 14+ требуется согласие пользователя перед каждой новой сессией захвата; пользователь видит активную сессию и может её остановить. Android 15 дополнительно скрывает часть чувствительного содержимого при демонстрации экрана.

**Сценарий, где есть смысл:** человек нажал «Проверить этот экран», выбрал окно мессенджера/платёжного экрана и получил локальный OCR-анализ. Для OCR доступны on-device варианты ML Kit; модель бывает встроенной в APK или загружаемой отдельно, что меняет размер приложения и первый запуск.

**Ограничения:** OCR может ошибаться на маленьком шрифте, тёмной теме, сложной верстке, смешанных языках и анимациях; скриншот может содержать пароли, остаток счёта, личные сообщения и коды. Постоянный захват разряжает батарею и противоречит цели минимального сбора.

**Рекомендация:** не делать фоновое наблюдение. Если нужна возможность проверки скриншота — пользователь выбирает его через Share/Photo Picker, изображение обрабатывается локально и удаляется после ответа. [Android MediaProjection](https://developer.android.com/media/grow/media-projection), [ML Kit Text Recognition](https://developers.google.com/ml-kit/vision/text-recognition/v2/android).

### 1.6 Буфер обмена — Android: только активное действие; Windows: высокий риск фонового режима

На Android 10+ фоновое приложение не должно получать чужой foreground clipboard так, как это было возможно на старых версиях; Android 13 показывает системное подтверждение копирования и автоматически очищает некоторые данные clipboard через время. Для безопасного продукта лучше дать кнопку «Вставить/проверить» в открытом приложении или принять текст через Sharesheet.

Windows WinRT предоставляет событие изменения буфера обмена и метод чтения содержимого. Это полезно для пользовательской кнопки «Проверить скопированные реквизиты», но пассивный обработчик может увидеть пароль, код, данные карты или семейную переписку, скопированные для другой задачи.

**Рекомендация:** не слушать буфер постоянно. Чтение — после нажатия пользователем; текст не сохраняется, анализ локальный. [Android secure clipboard handling](https://developer.android.com/privacy-and-security/risks/secure-clipboard-handling), [Windows Clipboard.ContentChanged](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.datatransfer.clipboard.contentchanged), [Windows copy/paste](https://learn.microsoft.com/en-us/windows/apps/develop/communication/copy-and-paste).

### 1.7 SMS — видеть уведомление можно, читать всю SMS-базу обычно нельзя

Если SMS-приложение публикует видимое уведомление, уже разрешённый notification listener может обработать именно его текст с теми же ограничениями приватности.

Google Play ограничивает `READ_SMS`, `RECEIVE_SMS` и call-log разрешения: обычно они допустимы только для приложения, выбранного пользователем SMS/Phone/Assistant обработчиком. Исключение против smishing существует, но политика требует показать значимую историю защиты, например подтверждения независимых тестов/публикаций. Для MVP без такого доказанного опыта рассчитывать на общее разрешение на все SMS не следует.

`SMS User Consent API` не является API для чтения любых чужих SMS: он рассчитан на один конкретный текст SMS с кодом подтверждения после действия пользователя в соответствующем verification-flow. `SMS Retriever` — автоматизация кода в том же узком сценарии.

**Рекомендация:** для защиты от мошеннических SMS использовать уведомление/Share, не делать продукт приложением SMS по умолчанию только ради сбора данных. [SMS User Consent API](https://developers.google.com/identity/sms-retriever/user-consent/overview), [правила SMS и Call Log в Google Play](https://support.google.com/googleplay/android-developer/answer/10208820).

### 1.8 Телефонные вызовы — P2 как отдельная функция Caller ID

`CallScreeningService` может получить детали входящего или исходящего вызова, если пользователь выбрал приложение как call-screening приложение. Оно может принимать решение о блокировке/показе входящего звонка; системный фреймворк требует ответить быстро — в частности, для входящего звонка указан срок 5 секунд.

**Что полезно:** номер вызова, направление и репутация номера могут подсказать, что перед переводом было давление по звонку. Это не даёт расшифровку разговора.

**Ограничения:** подмена номера, новые номера и звонок с аккаунта родственника ломают простую проверку по номеру. Доступ к журналу вызовов отдельно ограничен Google Play правилами default Phone/Assistant-role. Анализировать звонок можно лишь в рамках отдельной прозрачной функции и соответствующего разрешения.

Android захват воспроизводимого аудио другим приложением требует `RECORD_AUDIO` и согласия MediaProjection, а приложение-источник и тип аудио должны разрешать захват; телефонная связь не входит в разрешённые usage-типы обычного playback capture. Фоновая запись разговоров не должна быть частью ContextShield. [CallScreeningService](https://developer.android.com/reference/android/telecom/CallScreeningService), [ограничения захвата аудио](https://developer.android.com/media/platform/av-capture).

### 1.9 Полная адресная книга — не брать; system picker одного контакта — полезная проверка

`READ_CONTACTS` и `READ_CALENDAR` — чувствительные runtime-разрешения.

**Возможная польза:** локально проверить, встречается ли номер отправителя в контактах пользователя, или сравнить заявленное событие с календарём.

**Почему сигнал слабый:** имя контакта не проверяет человека; SIM/аккаунт/мессенджер могут быть захвачены; незнакомый контакт часто легитимен; знакомый может сам стать жертвой. Совпадение с календарём тоже не доказывает безопасность. Полная адресная книга сама по себе не нужна для определения социальной инженерии и при загрузке в облако раскрывает сведения о третьих лицах, которые не устанавливали приложение.

**Рекомендация:** не читать всю адресную книгу и не сопоставлять display name/ник с контактным именем как proof of identity. Для отдельного «проверить близкого» действия пользователь может выбрать конкретный контакт системным picker, после чего приложение получает только нужный телефон и открывает `ACTION_DIAL`; имя/номер не отправляются в облако и не превращаются в постоянный trust score. Убедиться на минимальной и целевой версиях Android, что выбранная URI permission достаточна без широкого `READ_CONTACTS`; не реализовывать обход, если нет. [Android `PickContact`](https://developer.android.com/reference/androidx/activity/result/contract/ActivityResultContracts.PickContact), [Android permission API](https://developer.android.com/reference/android/Manifest.permission).

### 1.10 Установленные приложения — P2 только для точечной проверки remote-access риска

Начиная с Android 11, список видимых пакетов ограничен package visibility. `QUERY_ALL_PACKAGES` раскрывает весь перечень установленных приложений, считается широким разрешением и требует оправданной основной функции/проверки Play. Для ограниченного продукта предпочтительнее объявить только нужные известные пакеты, если конкретный кейс это оправдывает.

**Потенциальный признак:** перед переводом установлено/активно использовалось приложение удалённого управления. Сам факт установки не доказывает, что кто-либо управляет устройством или что перевод мошеннический; полный список приложений раскрывает интересы пользователя.

**Рекомендация:** не запрашивать `QUERY_ALL_PACKAGES` для демо. При будущем партнёрском bank-flow — локальная проверка узкого allowlist только после информированного согласия, без выгрузки списка. [Android package visibility](https://developer.android.com/training/package-visibility/declaring).

### 1.11 Геолокация, камера, микрофон и сеть — не основной антифрод-контекст

- **Геолокация:** Android различает approximate/precise и foreground/background. Background location нужно отдельно объявлять и объяснять; у Google Play есть собственная политика для него. «Необычное место» может быть слабой подсказкой банковскому антифроду, но слабо определяет мошенническое сообщение и раскрывает перемещения. Предпочтительнее банковская транзакционная телеметрия или один короткий coarse-сигнал на этапе перевода, если банк доказал пользу. [Location permissions](https://developer.android.com/develop/sensors-and-location/location/permissions).
- **Камера/изображения:** полезный разовый сценарий — пользователь сам сканирует QR или выбирает скриншот. Анализировать нужно URL/платёжный URI и показать его пользователю, не включать камеру в фоне.
- **Микрофон:** фоновое прослушивание не нужно. Для playback capture других приложений Android требует разрешения и MediaProjection, а захватываемость зависит от явной политики приложения-источника и аудиокласса; обычный телефонный разговор не является поддерживаемым содержимым для такого перехвата. [Android audio capture](https://developer.android.com/media/platform/av-capture).
- **VPN/трафик:** `VpnService` требует системного подтверждения и устанавливает активный VPN; одновременно у пользователя может быть только один prepared VPN-сервис. VPN способен обрабатывать сетевые пакеты, но это не универсальный путь к тексту чата: HTTPS/TLS и end-to-end encryption закрывают содержимое, а certificate pinning может дополнительно препятствовать посреднику. Не перехватывать и не расшифровывать трафик мессенджеров. [Android VPN](https://developer.android.com/develop/connectivity/vpn), [Android network security/TLS configuration](https://developer.android.com/privacy-and-security/security-config).
- **Integrity:** Google Play Integrity может дать серверу проверенные признаки подлинности приложения/устройства и доступности приложения, но не говорит, является ли получатель денег мошенником или уязвим ли человек к давлению. Это сигнал защиты банковской сессии, а не граф переписки. [Play Integrity verdicts](https://developer.android.com/google/play/integrity/verdicts).

## 2. Windows

### 2.1 Системные toast-уведомления — P0/P1, уже есть отдельный UWP-прототип

`UserNotificationListener` позволяет читать доступные Windows уведомления. Приложение должно иметь capability `userNotificationListener` в manifest и вызвать `RequestAccessAsync` с UI-потока. Пользователь может разрешить или запретить доступ, а затем отозвать его в настройках. Документация описывает чтение текущих app toast-уведомлений и событие изменения.

**Ценность:** тот же временной граф, что на Android, для уведомлений мессенджеров и приложений, которые действительно публикуют Windows toast.

**Ограничения:** уведомления, скрытые самой программой, внутренние in-app чаты и содержимое за пределами toast недоступны; при отзыве доступа API может вернуть пустой результат; нельзя обещать анализ каждого сообщения. Прототип в репозитории уже использует этот listener, но сборка/установка UWP требует Windows developer tooling и выдачи доступа в Windows.

**Рекомендация:** оставить системный источник и показать индикатор разрешения/последнего события; уведомления анализировать локально. [Microsoft: Notification listener](https://learn.microsoft.com/en-us/windows/uwp/design/shell/tiles-and-notifications/notification-listener), [UserNotificationListener API](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.management.usernotificationlistener).

### 2.2 UI Automation других приложений — P2, только узкий foreground-сценарий

Windows UI Automation может читать доступные свойства большинства UI-элементов и используется assistive technologies и тестовыми инструментами.

**Потенциальная польза:** прочитать заголовок окна/доступный текст активной беседы или страницы, когда нет toast.

**Ограничения:** «большинство» не означает «все». Пользовательский интерфейс может быть недоступен автоматизации, защищён, нарисован без accessibility tree или работать с другим уровнем целостности. Windows блокирует взаимодействие обычного процесса с приложением повышенного уровня, а secure desktop/UAC ограничивает автоматизацию. Повышать права приложения ради обхода этих границ нельзя.

**Рекомендация:** не сканировать desktop/UI постоянно. Если для конкретной задачи понадобится UIA, пользователь выбирает активное приложение, видит индикатор, анализ идёт локально и только в момент проверки. Для банка лучше официальный SDK, не чтение UI. [Microsoft UI Automation overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview), [Windows ограничения UIPI](https://learn.microsoft.com/en-us/power-automate/desktop-flows/how-to/enable-ui-access).

### 2.3 Захват окна через Windows Graphics Capture — P2, только пользовательский picker

Windows API предоставляет системный picker, в котором человек выбирает окно или дисплей; документированное назначение — захват выбранного окружения, а не бесшумное чтение всего компьютера.

**Рекомендация:** если нужен OCR на ноутбуке, кнопка «Проверить окно», выбор окна системным UI, OCR на устройстве и уничтожение кадра. Скрытый continuous screen recorder не включать. [Windows screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [Windows.Graphics.Capture](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture).

### 2.4 Буфер обмена Windows — P2 только по нажатию

WinRT `Clipboard` умеет сообщить об изменении и получить текущее содержимое. Технически это может поймать скопированные реквизиты или подозрительную ссылку, но также пароли и любые случайно скопированные личные данные. Содержимое clipboard не доказывает, куда пользователь собирается перевести деньги.

**Рекомендация:** явная кнопка «Проверить скопированные реквизиты», без фоновой истории clipboard и без облачной отправки без второго подтверждения.

### 2.5 Процессы и активное окно — P2, слабый дополнительный сигнал

Desktop-клиент или подписанный helper может определить foreground-процесс/название окна или ограниченный набор работающих программ. Это может подсказать, что открыт браузер/банк/программа удалённого доступа, но не раскрывает сообщение и не подтверждает мошенничество. UWP-песочница имеет более узкие возможности, чем desktop helper; установка helper меняет модель безопасности.

**Рекомендация:** никаких глобальных key hooks и записи клавиатуры. Если конкретный сценарий требует контекста активного окна — получать только имя окна/процесса, только при проверке и только после ясного opt-in.

## 3. Браузер, почта и мессенджеры на компьютере

### 3.1 Браузерное расширение — P1, хорошее расширение для ссылок

Расширение Chromium может использовать `activeTab`: браузер временно даёт доступ к URL/заголовку текущей вкладки после явного действия пользователя, например клика на кнопку расширения. Доступ прекращается при переходе на другой сайт или закрытии вкладки. Для полноценного анализа DOM требуется `scripting` и запуск скрипта в этой вкладке; постоянный доступ ко всем сайтам потребовал бы гораздо более широких host permissions.

**Что проверять:** домен и punycode/сходство с брендом; URL, скопированный из сообщения; форму/страницу только в активной вкладке после нажатия; признаки редиректа при безопасном запросе к URL.

**Что не собирать:** полную историю браузера, все открытые вкладки и текст всех страниц. URL может содержать уникальные токены, invite-коды, номера заказов или персональные параметры; перед любой облачной проверкой их нужно удалить.

**Рекомендация:** extension с `activeTab` и минимальными permissions; анализ текущей ссылки по кнопке/контекстному меню, доменное решение локально или через узкий endpoint. [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab).

### 3.2 Outlook — выбрать одно письмо, а не читать весь mailbox

Outlook add-in с уровнем `ReadItem` читает свойства текущего элемента, открытого пользователем в Outlook. Это позволяет сделать кнопку «Проверить это письмо» и оценить видимый отправитель, домен, ссылки и тело текущего письма.

Microsoft Graph `Mail.Read` — другая и более широкая схема: delegated-разрешение даёт чтение почты вошедшего пользователя, а application permission может охватывать почтовые ящики организации. Это не следует запрашивать только ради антифрод-демо.

**Рекомендация:** current-item Outlook add-in с минимальной item-scoped permission; Graph и подписки на все письма — только если отдельный продукт/партнёр действительно требует фоновой почтовой защиты и пользователь/администратор дал соответствующее согласие. [Outlook add-in permissions](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/understanding-outlook-add-in-permissions), [Microsoft Graph Mail.Read](https://learn.microsoft.com/en-us/graph/permissions-reference), [Graph get message](https://learn.microsoft.com/en-us/graph/api/message-get).

### 3.3 Telegram, WhatsApp и другие личные чаты

Публичные API мессенджеров — не универсальный доступ к личному аккаунту пользователя. Например, Telegram Bot получает сообщения, адресованные боту, а в группах по умолчанию — только релевантные сообщения; чтобы видеть обычные групповые сообщения, боту нужен иной видимый статус/настройка. WhatsApp Business Platform относится к обмену от имени бизнес-номера и соответствующего Business API, а не к чтению личного WhatsApp-архива владельца телефона.

**Поддерживаемые пути для личных сообщений:** уведомление, системный Share/Forward пользователем или официальный интеграционный сценарий, если конкретный сервис действительно предоставляет его и человек его явно подключил. Не использовать неофициальные клиентские библиотеки, скрейпинг закрытого хранилища, перехват локальной базы мессенджера или копирование сессии пользователя.

[Telegram Bots FAQ](https://core.telegram.org/bots/faq), [Telegram Bots introduction](https://core.telegram.org/bots), [WhatsApp Business Platform](https://developers.facebook.com/documentation/business-messaging/whatsapp/overview).

## 4. Самый важный канал: банк и конкретная операция

### 4.1 SDK внутри банковского приложения — P0, единственный полноценный transaction gate

Банковское приложение перед подтверждением само знает фактический перевод и может передать SDK только необходимые поля. Минимальный интерфейс события:

- случайный ID эпизода/операции;
- сумма и валюта в диапазоне, если точная сумма не нужна модели;
- псевдонимизированный токен получателя/счёта и страна/банк назначения, если доступны;
- получатель новый/повторный, дата первого успешного перевода ему, число предыдущих операций в агрегате;
- изменились ли реквизиты/способ оплаты в текущем процессе;
- тип операции: карта, быстрый перевод, перевод по телефону/QR, крипто/наличные — только если такой тип реально есть у банка;
- локальный контекст сообщений: категории признаков, относительный возраст событий, приложение-категория и confidence;
- версия модели, provenance каждого признака и понятные причины ответа.

SDK возвращает категориальные рекомендации: `allow`, `step_up`, `cooldown/confirm recipient by known channel`, `manual review` или `deny` согласно правилам банка. **Реальное решение остаётся у банка**, где есть transaction authorization, антифрод-правила, аудит и обработка жалоб. SDK не должен получать PIN, CVV, пароль, содержимое клавиатуры, секреты входа или необработанный PAN.

**Почему это сильнее любых фоновых сигналов:** только этот источник связывает сообщения с конкретным получателем и реальным переводом. Сообщение «срочно переведи тысячу» без операции не знает, кому, куда и сколько пользователь собирается отправить; история приложения не заменяет это.

Документ проекта правильно определяет банковское событие как канал, нужный для настоящей блокировки. Текущий экран «Перевести» в APK — демонстрационный gate внутри ContextShield, не сторонняя банковская транзакция.

### 4.2 Open Banking / Account Information Services — полезно для истории, не равно кнопке блокировки

С согласия пользователя Account Information Service Provider может получать предусмотренную API account information по подключённым платёжным счетам. Конкретные поля, срок согласия, обновление и страны зависят от юрисдикции и банка.

**Возможная ценность:** проверить, есть ли у пользователя повторные переводы получателю или новая финансовая активность; использовать историю для локальной базовой линии.

**Что не гарантируется:** намерение сделать именно текущий перевод, данные нового получателя до исполнения или возможность отменить/задержать платёж. Read-only история постфактум слабее bank SDK на этапе подтверждения. В Великобритании Open Banking Standard описывает доступ AIS к информации счёта при явном согласии пользователя; это не универсальное разрешение для любых рынков.

**Рекомендация:** не подключать в первом демо. Если добавится, использовать regulated provider, scopes с минимальным набором данных, ограниченный срок consent и кнопку отзыва/удаления. [Open Banking AIS customer consent](https://standards.openbanking.org.uk/customer-experience-guidelines/account-information-services/latest/).

### 4.3 Короткие ответы самого пользователя — P0, без новых системных разрешений

В нужный момент можно задать один-два контекстных вопроса, только если локальный анализ уже видит риск: «Получателя добавили сегодня?», «Просили никому не говорить?», «Код/экран/удалённое управление просили передать?», «Вы проверили просьбу звонком на сохранённый номер, а не по номеру из сообщения?».

**Почему полезно:** пользователь знает отношения, привычный способ связи и изменение ситуации, чего не видно из текста или API. Такой короткий ответ может сильнее различить обычный семейный расчёт и неожиданную просьбу с нового аккаунта, сопровождаемую давлением или новыми платёжными реквизитами.

**Нюансы:** не превращать это в длинный опрос после каждого уведомления; не просить имя, телефон, адрес или всю переписку; ответ «знакомый» не доказывает подлинность — аккаунт могли захватить. Показывать конкретный следующий безопасный шаг (проверить по уже известному каналу), не обещать абсолютную точность.

### 4.4 Собственные банковские сигналы сессии — P0 только в bank/backend интеграции

Если банк/платёжный сервис является партнёром, наиболее полезны не дополнительные данные со смартфона, а события, которыми этот банк уже управляет:

- новый ли получатель и менялись ли его реквизиты;
- сумма/частота перевода относительно собственного профиля счёта;
- новый девайс/новая сессия, сброс пароля или нетипичная смена способа аутентификации;
- не было ли непосредственно перед переводом добавления получателя, изменения лимита, отмены безопасного предупреждения;
- история переводов получателю и агрегированная репутация destination account, если у банка есть законное основание и достаточная достоверность;
- ранее подтверждённые пользователем случаи мошенничества, возвраты/chargeback и сигналы банковского антифрод-контроля;
- недавняя смена SIM/перенос номера или риск владения номером — только если оператор/партнёр официально предоставляет такой сигнал, не пытаться угадывать его по уведомлениям.

Это примеры полей для обсуждения с банком, а не утверждение, что каждый банк или open-banking API их отдаёт. Их нужно передавать в SDK как минимальные категории/токены, а не копировать полную банковскую историю в телефон или LLM. Ни сигнал нового устройства, ни повышение суммы не должны автоматически означать мошенничество: это контекст для дополнительной проверки, которую контролирует банк.

## 5. Другие данные и насколько они полезны

| Источник | Реальный сигнал | Польза для антифрода | Вердикт |
|---|---|---|---|
| **Номер/имя в выбранном уведомлении** | То, что мессенджер показал в notification | Помогает связать запросы в одном эпизоде; имя не удостоверяет собеседника | P0 в локальном контексте |
| **URL из сообщения/Share** | Домен, redirect/shortener, punycode, tracking/query параметры | Сильная отдельная ветка для phishing/fake-bank; не равна риску перевода | P0/P1, проверять URL локально/узким сервисом |
| **Получатель и смена реквизитов из банка** | Новый/известный beneficiary, изменённые данные, сумма, тип перевода | Наиболее прямой сигнал риска самого перевода | P0, через банк |
| **Порядок сообщений и действий** | Срочность → секретность → звонок → новый платёж/remote access | Показывает сценарий социальной инженерии лучше одиночного слова | P0, локальный граф короткого эпизода |
| **Недавние app-usage события** | Какое приложение открывалось, когда | Может подкрепить remote-access сценарий; причинность неизвестна | P2, opt-in и эксперимент |
| **Вызов/номер** | Номер и направление звонка через CallScreening role | Репутация номера полезна против call scams; caller ID можно подделать | P2 отдельный модуль |
| **Контакты адресной книги** | Есть ли номер в сохранённых контактах | Слабый признак знакомства, не доверия/подлинности | Не просить всю адресную книгу |
| **Геолокация** | Приблизительное/точное место устройства | Слабая проверка невозможного перемещения для банка, почти не говорит о содержании разговора | Не брать постоянно; при доказанной банковской нужде только короткий foreground-сигнал |
| **Список установленных приложений** | Наличие remote support/crypto приложения | Установка не означает запуск/давление | Не брать полный список; точечный allowlist только при необходимости |
| **Device/app integrity** | Подлинность приложения/устройства, часть риск-среды | Помогает защищать банковскую сессию от tampering; не определяет жертву/мошенника | P1 у банковского backend |
| **IP/Wi-Fi/VPN тип подключения** | Сетевой путь и подключённый VPN | Низкая точность гео/перехвата; содержание TLS скрыто | Не использовать как основной fraud score |
| **Календарь** | Запланированное событие/контакт | Может подсказать известный контекст, но не подтверждает разговор | Не запрашивать по умолчанию |
| **Скриншот/OCR** | Текст выбранного окна/изображения | Помогает, когда нет уведомления или надо прочитать QR | Только пользователь выбирает конкретный кадр |
| **Клавиатурная динамика/нажатия** | Скорость, последовательность, текст ввода | Внутри bank SDK может быть исследуемым поведенческим сигналом, но вне собственного UI становится наблюдением за вводом | Не делать keylogger; не собирать текст ввода |

Таблица ценности — продуктовая оценка, а не измеренная метрика для этого приложения. Каждый признак нужно проверять на размеченном наборе и проверять, снизил ли он false-positive rate при том же recall.

## 6. Какие данные нельзя получить надёжно или не стоит получать

1. **Внутренняя база чужого мессенджера.** Android изолирует данные приложений sandbox-ом; другой обычный app не читает приватные файлы мессенджера без специально предоставленного публичного интерфейса. [Android Application Sandbox](https://source.android.com/docs/security/app-sandbox).
2. **Полная переписка из E2E-зашифрованного приложения.** Системное уведомление или пользовательский Share — это то, что ОС/пользователь явно отдали; публичного универсального API к истории чатов нет.
3. **Любые SMS без роли/исключения Play.** Сторонний антифрод-помощник не получает blanket `READ_SMS` по умолчанию.
4. **Текст телефонного разговора из CallScreeningService.** Этот API предназначен для данных вызова/скрининга, не транскрипции.
5. **Скрытое аудио других приложений.** Playback capture требует системного consent и условий совместимости приложения-источника; голосовая связь обычным способом не снимается.
6. **Содержимое браузера на всех сайтах без отдельного расширения и разрешений.** `activeTab` даёт узкий доступ после действия пользователя; общий host permission гораздо шире.
7. **Настоящая блокировка платежа из стороннего приложения.** Без банковского SDK/API можно запретить только перевод в собственной демонстрации, но не в установленном банковском приложении.
8. **Стопроцентно надёжную личность отправителя по имени/номеру/аватарке.** Это отображаемые идентификаторы, а не доказательство владения человеком/аккаунтом.
9. **Достоверный вывод «пользователь доверчивый/его легко обмануть» из скользящей истории.** Такой ярлык не нужен для защиты транзакции, может быть ошибочным и превращается в долговременный поведенческий профиль.

Не подключать: фоновый keylogging, скрытый экранный OCR/запись, постоянный микрофон, незаметный clipboard-перехват, постоянный GPS, обход Android OTP-redaction, root/bypass средств защиты банка, MITM трафика мессенджеров, scraping WhatsApp/Telegram private storage.

## 7. Как построить граф контекста, а не граф слежения

Граф нужен, чтобы объяснять **текущую подозрительную ситуацию** и её историю, а не строить постоянное досье на пользователя и его круг общения.

### 7.1 Минимальные сущности

- `episode`: локальный эпизод проверки/перевода;
- `message_event`: категория признаков и грубое время, без полного тела сообщения;
- `source_app_category`: например `messenger`, `sms_app`, `browser`, без лишнего device inventory;
- `sender_account_token`: опциональный локальный keyed-HMAC только от официального opaque account/conversation ID, если интеграция действительно его выдаёт и документирует стабильность; если ID нет — узел отправителя не создаётся. Ник/display name никогда не превращается в sender ID;
- `identity_continuity`: `verified_account_continuity | unknown | name_changed | conflict`; даже стабильный platform account ID не подтверждает, что аккаунтом сейчас управляет тот же человек;
- `link_domain`: registrable domain без query, fragment, invite token и tracking параметров;
- `payee_local_token`: только банковский токен получателя, если его передал банк;
- `transfer_event`: диапазон суммы, валюта, новое/повторное направление и результат по банковскому API;
- `feature`: например urgency, secrecy, authority impersonation, request for code, remote access, account change;
- `provenance`: источник сигнала, версия парсера, confidence, время наблюдения и причина, по которой сигнал считается доступным.

### 7.2 Полезные рёбра и последовательности

`message → contains_link → domain`  
`message → asks_for → transfer/code/remote_access`  
`message → attributed_locally_to → sender_account_token` (только если официальный стабильный ID доступен; иначе связь отсутствует)  
`episode → precedes → call_or_app_switch`  
`episode → associated_with → transfer_event`  
`transfer_event → pays → payee_local_token`

Примеры полезной последовательности: «псевдо-банк просит код»; «родственник внезапно заявляет о ЧП, просит секретность, затем просит новый счёт»; «пользователь перешёл по домену-подделке и добавил нового получателя». Одно слово «срочно» или сам факт нового контакта не должен автоматически блокировать платёж.

### 7.3 Хранение и идентичность

- Исходный текст обрабатывается в памяти и удаляется после вычисления признаков.
- На устройстве может оставаться короткое скользящее окно событий. Для графа более длинное окно, например до 30 дней, имеет смысл только если нужен повторный контекст; хранить тогда категориальные рёбра, не тексты, давать очистку и не включать это незаметно.
- Имя/ник не является pseudonym key и не используется для linking/trust. Если источник не выдал stable ID, identity остаётся `unknown`; совпадение имени с контактом не создаёт ребро к человеку.
- Stable account token — это лишь непрерывность аккаунта, не доказательство его владельца: аккаунт может быть захвачен. Display name change помечается, но не считается самостоятельным fraud signal.
- Псевдоним — не анонимность. Если account token можно связать с человеком дополнительным ключом/контекстом, он остаётся персональными данными. Данные третьего лица (собеседника) тоже требуют минимизации.
- В облако для второго мнения лучше отправлять текущий граф эпизода как агрегат: `3 сообщения за 20 минут`, `urgency=true`, `remote_access_app_opened=true`, `identity_continuity=unknown`, `new_payee=true`, `amount_bucket=medium`. Не отправлять stable ID, телефон, имя, полный URL, историю приложений или сырой текст.
- Если для качества модели необходим кусок текста, отправка должна быть отдельной кнопкой с предварительным просмотром. Замена имён эвристикой — это де-идентификация, не гарантия анонимности; уникальный текст может узнать человека.
- Граф не присваивает людям постоянное `fraudster_score` и пользователям профиль «поддаётся обману». Модель оценивает риск **эпизода/конкретной транзакции** с причинами и неопределённостью.

Это дизайн-рекомендации, а не обязательные требования API. В ЕС GDPR определяет персональные данные широко, включая онлайн-идентификаторы и факторы социальной/экономической идентичности; псевдонимизация сама по себе не выводит данные из режима personal data. Для целевого продукта нужны purpose limitation, data minimisation, privacy by design/default и оценка DPIA, если обработка вероятно создаёт высокий риск. Статья 22 отдельно описывает решения, принимаемые только автоматически и имеющие юридический или аналогично значимый эффект; банковское блокирование платежа надо проектировать вместе с банком и юристом, с понятным объяснением, ручным пересмотром/оспариванием и сохранением банковского контроля. Применимость зависит от стран и ролей участников. [GDPR, EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679).

## 8. Рекомендуемый порядок работ для текущего ContextShield

### P0 — сделать демонстрацию честной и функционально сильной

1. Оставить Android notification listener как системный канал; честно показывать разрешение, скрытый preview и ограничения sender identity.
2. Реализовать контекстный граф и demo-bank: `notification → optional remote-access app event → TransferAttempt`; `allow/step_up/hold` управляет только своей тестовой кнопкой.
3. Сделать system contact picker + `ACTION_DIAL` отдельной кнопкой out-of-band проверки; не доверять имени в сообщении и не просить `READ_CONTACTS` на всю книгу.
4. Провести UsageStats feasibility spike с узким allowlist и однократным 15-минутным окном после активного эпизода. Не включать сигнал в decision policy, пока не измерены Android/OEM coverage и false-positive effect.
5. В облако отправлять только согласованные категории; raw text не посылать автоматически и не делать запрос на каждое уведомление.
6. Добавить тестовый режим на синтетических сообщениях/сценариях, включая nickname spoofing, legitimate rename, remote-support false positive и benign family transfer.

### P1 — будущие платформы/дополнительные модули, вне Android-first MVP

1. Windows toast listener/browser add-in сохранять как отдельный будущий проектный поток; не делать его критерием Android выпуска.
2. Добавлять Outlook/browser integration только после отдельного permission/privacy review.
3. Официальный bank SDK контракт нужен для будущего реального transaction gate; текущая песочница не двигает деньги.
4. Локальный threat-intel для доменов/телефонных диапазонов с provenance, сроком актуальности и объяснением совпадения — отдельная фаза.

### P2 — только после оценки выигрыша

Отдельная проверка вызова через `CallScreeningService`; разовый MediaProjection выбранного окна. Добавлять только как самостоятельные opt-in функции после offline evaluation и проверки требований Android/Google Play.

### Не включать в MVP

Полная адресная книга, постоянная геолокация, чтение всех SMS/звонков, фоновый clipboard/экран/микрофон, глобальная история браузера, список всех установленных приложений, неофициальная интеграция с закрытыми мессенджерами.

## 9. Что реализовано в текущем репозитории

По исходникам ветки проекта на дату проверки:

- **Android:** `NotificationListenerService`, локальная классификация уведомлений, локальная история/граф риска и демонстрационная кнопка перевода. В `AndroidManifest.xml` нет UsageStats opt-in, system contact verification flow, Accessibility, MediaProjection, SMS или call-screening.
- **Windows:** UWP-прототип с `UserNotificationListener` и системной capability `userNotificationListener`.
- **Банк:** отдельного реального банковского API/SDK нет; перевод — симуляция внутри демонстрационного приложения.
- **Браузер/почта:** расширения и Outlook add-in в проекте нет.
- **Облако:** OpenRouter включается пользователем отдельно; до передачи применяется локальная эвристическая очистка. Очистка не является доказательством полной анонимности.

Таким образом, «всё, что можно технически прочитать» и «все полезные каналы, которые должны быть в MVP» — разные списки. Для полноценного показа разумно показать 2 реально подключённых системных источника плюс явный Share-путь и банковский transaction gate в эмуляторе; дополнительные источники включать только там, где есть конкретная гипотеза и понятный контроль пользователя.
